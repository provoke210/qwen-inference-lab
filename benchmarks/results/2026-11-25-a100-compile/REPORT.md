# 录图前先 torch.compile：A100 结果

2026-11-25，1 × A100-SXM4-40GB，torch 2.13.0+cu129，vLLM 0.30.0，分支 `compile-decode`（在 `main` 2f92d7f 之上）。作业脚本：本目录 `job.pbs`（对比）和 `profile/job.pbs`（性能分析）。

## 改了什么

- 新选项 `Engine(..., cuda_graph=True, compile_decode=True)`：引擎启动时先用 `torch.compile`（Inductor）编译解码计算，每个批大小编译一次，再录 CUDA Graph。Inductor 会把矩阵乘之间零碎的逐元素运算融合成少数几个 kernel。默认关闭。
- 模型的解码拆出一个不带 `@torch.inference_mode()` 的 `decode_compute`：`torch.compile` 直接编译带这个装饰器的函数会失败。
- **开启编译时，写 KV cache 的那一步不参与编译。** 第一版没有这样做，结果每步慢到 34 ms（不编译时约 4.5 ms）：在编译后的代码里，往整块 KV cache 的一个切片原地写入，会被改写成“复制整块 cache”，每层都复制一次。现在这一步保持原样（两个小 kernel），编译后的代码只读 cache，代价是编译结果在每层的写入处断开。这个处理只作用于开启了 `compile_decode` 的引擎，正常导入 qil 不会加载编译器。

## 正确性

| 检查 | 结果 |
|---|---|
| 全部测试（A100） | ✅ 116 passed，包括新增的“编译后生成的 token 与 eager 相同” |
| 逐 token 对比：仅 graph、graph + 编译、vLLM，4 组 × 每次运行 × 每个负载 | ✅ 全部相同 |

编译后的计算在 CPU 上与 eager 的最大差约 6e-8（融合后舍入顺序不同），没有影响任何生成的 token。

## 每步解码（profile/，0.6B FP32，单请求，prompt 128）

| | 仅 graph | graph + 编译 |
|---|---:|---:|
| 每步时间（中位数） | 4.53 ms | 4.19 ms |
| 其中 GPU 时间 | 4.54 ms | 3.62 ms |

编译让 GPU 时间少了 20%，但每步时间只少了 7%：编译后每步在 3.7 ms 和 4.2 ms 两档之间跳动，原因还没查。

## 启动时间

| | 仅 graph | graph + 编译 |
|---|---:|---:|
| 引擎启动（有编译缓存） | 1.5–16 s | 16–38 s |

第一轮（还带着那个问题的）运行在没有缓存时编译了 110–150 秒；这次命中了 Inductor 的磁盘缓存，所以只多了约 14–21 秒。换一台机器或升级 PyTorch 后第一次启动仍会是约 2 分钟。

## 结论

1. **编译有效，但收益有限：+1% 到 +15%，BF16 收益最大（+6% 到 +15%），4B FP32 几乎没有（+1% 到 +2%）。** 4B FP32 的时间主要在矩阵乘上，编译融合的逐元素运算本来就占得少。
2. **离 vLLM 默认模式现在是 45%–90%。** 差距最大的仍是 0.6B BF16 并发（45%–54%）。
3. **为什么比不上 vLLM 的编译**：vLLM 把注意力和 KV 写入做成自定义算子，编译时整层不断开，还有专门的融合 pass；我们这里编译结果在每层的 KV 写入处断开，只能在两次写入之间融合。
4. **建议作为可选项合并**（默认关闭）：输出不变、有提速，代价是启动多 15–40 秒（首次约 2 分钟）。

## 下一步

- **把 KV 写入注册成自定义算子**（`torch.library.custom_op`，声明它会修改 KV cache），这样编译时整层不断开，也不会复制整块 cache。这正是 vLLM 的做法，预计能再融合掉一批 kernel。
- 查清编译后每步时间在两档之间跳动的原因。
