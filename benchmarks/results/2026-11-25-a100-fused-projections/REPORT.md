# 合并 QKV 与 gate/up 矩阵乘：A100 前后对比

2026-11-25，1 × A100-SXM4-40GB，torch 2.13.0+cu129，vLLM 0.30.0。作业脚本见本目录 `job.pbs`，每组（一个模型 + 一种精度）在同一张 GPU 上依次运行：

| 设置 | 代码 |
|---|---|
| 改动前 graph | `main`（47a4215），paged 注意力 + CUDA Graph |
| 改动后 eager | 分支 `fuse-projections`，paged 注意力，不开 CUDA Graph |
| 改动后 graph | 分支 `fuse-projections`，paged 注意力 + CUDA Graph |
| vLLM 默认 | torch.compile + CUDA Graph |

负载与 `../2026-11-23-a100-vs-vllm/` 相同：4 个负载，每个请求生成 128 个 token，吞吐含 prefill，预热 1 次后取 3 次中位数。

## 改了什么

每层原来是 Q、K、V、gate、up 五次独立的矩阵乘，现在合成两次：`qkv`（一次算出 q/k/v 再切开）和 `gate_up`（一次算出 gate/up 再切开），每层少 3 个 kernel。checkpoint 格式不变：加载时把各个投影写进合并权重的对应行；张量并行时每张卡先取自己的那一份再拼。

## 结论

1. **CUDA Graph 模式下快了 3%–21%，输出完全不变。** 离 vLLM 默认模式的差距从 40%–86% 缩小到 43%–89%。
2. **4B FP32 并发 4 个提升最大（+17%–21%，现在是 vLLM 的 80%–82%）**：这种情况本来就是 GPU 矩阵乘跑满，三个小矩阵乘合成一个大的，GPU 利用率明显提高。
3. **0.6B 提升 6%–10%，4B 单请求和 BF16 只有 3%–5%**：每层少了 3 个 kernel，但还剩约 24 个，其中多数是逐元素运算。BF16 下矩阵乘本身就快，合并省下的比例更小。
4. **剩下的差距主要还是逐元素 kernel 太多**：0.6B BF16 并发时仍只有 vLLM 的 43%–47%。下一步应该融合这些运算（残差 + RMSNorm、SiLU × up、q/k norm + RoPE），或者对解码部分用 `torch.compile` 后再录图。
