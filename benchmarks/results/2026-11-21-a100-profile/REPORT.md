# 解码一步的时间花在哪：A100 性能分析

2026-11-21，作业 `benchmarks/nscc/profile.pbs`，脚本 `benchmarks/profile_decode.py`。
1 × A100-SXM4-40GB，AMD EPYC 7713，torch 2.13.0+cu129，eager 模式，代码为分支 `decode-profiling`（引擎代码与 PR #1 相同）。

## 结论

1. **小模型的瓶颈是 CPU 发射 GPU 运算，不是 GPU 算力。** Qwen3-0.6B 每解码一步要发射约 1,450–1,850 个 GPU kernel，GPU 实际只忙 7–15 ms，一步却要 21–26 ms，GPU 有 41%–70% 的时间在等 CPU。
2. **每层约 62 个 kernel，其中约 44 个是零碎的逐元素运算。** 每个 RMSNorm 拆成 6 个 kernel（每层 4 个 norm 共 24 个），每次 RoPE 旋转 7 个（每层 2 次共 14 个），真正的矩阵乘法每层只有 7 个。这些零碎运算还占了 0.6B GPU 时间的约 45%。
3. **调度、页表准备、采样都不是问题。** 调度 0.02 ms，准备页表约 0.3–0.4 ms，采样（含两次 CPU-GPU 同步）约 0.5 ms，加起来不到一步的 5%。
4. **Qwen3-4B 情况不同：并发 4 个请求时基本已经是 GPU 跑满**（dense 下 GPU 空闲只有 2%–7%），这时时间主要花在 FP32 的矩阵乘（MLP 一项 8–15 ms）和 dense 注意力的 KV 拷贝上。单请求时仍有约 30%–40% 的空闲。
5. **BF16 在 0.6B 上没有更快**：矩阵乘变快了，但 RMSNorm 里多了类型转换，每步 kernel 从 1,741 个增加到 2,083 个。
6. **paged 注意力的 GPU 时间更少，但 0.6B 单请求反而比 dense 慢约 2.8 ms**：Triton kernel 每次都要经过 Python 层发射，每层一次、共 28 次的发射开销抵消了它省下的 GPU 时间。

## 每步时间与 GPU 忙碌时间

## 一步之内的分解：Qwen3-0.6B，FP32，dense，单请求，prompt 128

每个运算都加了计时标记后跑 8 步取平均。标记本身会增加 CPU 时间（这时一步约 48 ms，而不加标记是 21 ms），所以 CPU 一栏只看**比例**；GPU 一栏和 kernel 数是准确的。

| 阶段 | 每步次数 | kernel / 步 | GPU (ms) | CPU 占比 |
|---|---:|---:|---:|---:|
| 调度 | 1 | 0 | 0.00 | 0.0% |
| 准备页表与位置 | 1 | 16 | 0.05 | 0.8% |
| RMSNorm（每层 4 个） | 112 | 672 | 2.21 | 26.6% |
| RoPE 旋转（每层 2 次） | 56 | 392 | 1.33 | 13.2% |
| 注意力（gather + repeat + SDPA） | 28 | 273 | 2.15 | 17.7% |
| QKV 投影 | 84 | 84 | 0.75 | 8.5% |
| MLP 三个投影 | 84 | 84 | 1.28 | 8.0% |
| 输出投影 o_proj | 28 | 28 | 0.28 | 3.0% |
| 写 KV cache | 28 | 56 | 0.27 | 3.8% |
| 层内其余（残差相加、SiLU、乘法） | 28 | 112 | 0.32 | 15.6% |
| 最终 norm + lm_head | 2 | 7 | 0.46 | 0.3% |
| 采样（含 CPU-GPU 同步） | 1 | 10 | 0.04 | 1.1% |
| 其余（embedding、RoPE 角度、入口检查） | — | 7 | 0.02 | 1.3% |
| **合计** | | **1741** | **9.17** | 100% |

CPU 一侧最耗时的单项是 `cudaLaunchKernel`（每步 1,452 次），其次是 `aten::mm`、`aten::mul`、`aten::add`、`aten::pow`、`aten::mean`。不加标记时平均每个 kernel 约 12 µs 的 CPU 开销（21 ms / 1,741），这就是“每步 23 ms 框架开销”的来源。

## 对下一步的含义

按预计收益排序：

1. **CUDA Graph（解码步）**：把一步的全部 kernel 录成一张图，每步只发射一次。理想情况下一步时间降到“GPU 忙”加上不到 1 ms 的调度和采样：0.6B 约 8–16 ms（现在 21–26 ms，约 1.6–3 倍），4B 单请求约 20–25 ms（现在 30–34 ms），4B 并发 4 个几乎不变。paged 注意力的 Triton 发射开销也会一起消失，届时 paged 应该会快于 dense。需要的改动：按并发数准备几组固定形状的输入缓冲区，页表宽度固定为上限，位置和 slot 从缓冲区读取。
2. **融合 RMSNorm 和 RoPE**：RMSNorm 改为 `torch.nn.functional.rms_norm` 或一个小 Triton kernel（6 → 1），RoPE 改为单个 kernel（7 → 1），每层 kernel 从约 62 个降到约 30 个。这一步改动小，能单独测出效果，而且 CUDA Graph 之后仍然能减少 GPU 时间（约 3 ms / 步）。需要验证与现在的 FP32 计算结果一致。
3. **4B 并发场景**：瓶颈在 GPU 计算，要靠 BF16 权重（MLP 矩阵乘减半）和 paged 注意力（不复制 KV），而不是 CUDA Graph。BF16 要先解决 RMSNorm 多出来的类型转换，以及已知的精度问题。

## 原始文件

- `Qwen3-*.json`：每个配置的逐步计时、两种标记粒度下的分阶段数据、耗时最多的 kernel 和 CPU 运算。
- `trace-Qwen3-0.6B-fp32-dense-b1.json.gz`：0.6B dense 单请求 8 步的完整时间线。解压后拖进 <https://ui.perfetto.dev> 即可查看 CPU 发射和 GPU 执行的对应关系。
- `*.log`、`status.tsv`、`environment.txt`：作业输出与环境。

## 测量说明

- 每个配置先跑 8 步预热，再计时 32 步（不开 profiler），最后用 profiler 记录 2 × 8 步：一次只标记阶段和整层，一次标记到每个运算。
- 0.6B dense 单请求的“只标记阶段”那组里，第一步包含 profiler 启动开销（193 ms），所以本报告的分解用“标记到每个运算”那组。
- 引擎代码没有改动；计时标记只在 profiler 运行期间临时加上，每个配置结束后都会检查已全部移除。
