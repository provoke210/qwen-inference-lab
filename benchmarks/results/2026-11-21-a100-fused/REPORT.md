# 融合 RMSNorm 与 RoPE：A100 前后对比

2026-11-21，1 × A100-SXM4-40GB，torch 2.13.0+cu129，FP32 除非注明，eager 模式。
“前”是分支 `decode-profiling` 改动前的代码（与 PR #1 相同），数据来自 `../2026-11-21-a100-profile/`；“后”是本次改动，数据在本目录 `profile/`。两次用同一个脚本 `benchmarks/profile_decode.py`、同样的配置。

## 改了什么

- **RMSNorm**：原来是 `square → mean → +eps → rsqrt → 乘 → 乘权重` 6 个 kernel，现在用 `F.rms_norm`（torch 2.13 在 CUDA 上是一个融合 kernel）再乘权重，共 2 个。计算顺序不变：在 FP32 里归一化，转回原精度，再乘权重。
- **RoPE**：`cos` 预先复制到两半、`sin` 预先带上符号（`-sin, sin`），一次旋转变成 `x*cos + roll(x)*sin`；q 和 k 拼在一起一次旋转。每层从 14 个 kernel 变为 5 个，结果与原来**逐位相同**（单元测试验证）。
- paged 注意力前加了一次 `.contiguous()`（q 现在是旋转结果的一个视图；单请求时不产生 kernel）。

改动只在 `qil/model.py` 和 `qil/attention.py`。

## 结论

1. **每步 kernel 数减少约 40%，GPU 时间减少 15%–37%，输出完全不变。**
2. **4B 受益最多（单请求快 22%–28%）**：4B 本来有一部分时间是 GPU 在算，这次同时省了 CPU 发射和 GPU 计算。
3. **0.6B 只快了 3%–15%**：少发射约 700 个 kernel 只省了约 3 ms，平均每个 4 µs，比原先估计的每个 12 µs 少得多。说明剩下的 CPU 开销大部分不在 kernel 数，而在每次 Python 调用 PyTorch 模块和运算的固定成本。0.6B 的 GPU 仍有 55%–78% 的时间在空等，这部分只能靠 CUDA Graph 把整步录成一张图来消除。
4. **BF16 现在比 FP32 慢得少了**：类型转换的 kernel 随 RMSNorm 一起减少，0.6B BF16 单请求 19.1 ms，FP32 是 18.1 ms。
